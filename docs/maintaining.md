# Maintaining agent-team

The maintainer's handbook: sorting issues, reviewing pull requests, cutting a release, the private
word list, the generated files, the fact sheet, and publishing the repository for the first time.
Who maintains the project and how decisions are made is in [GOVERNANCE.md](../GOVERNANCE.md); how to
contribute is in [CONTRIBUTING.md](../CONTRIBUTING.md).

## Triage

Every issue arrives from a form with two labels: `needs-triage` and its kind (`bug`, `enhancement`
or `seat-proposal`). Blank issues are off; questions are sent to Discussions and security reports to
the Security tab by `.github/ISSUE_TEMPLATE/config.yml`.

1. **Read it and fix the kind label.** A feature request that is really a missing doc becomes
   `documentation`; a bug report that is a usage question becomes `question`.
2. **Reproduce a bug** on an invented project before accepting it: the reporter's plugin version
   (`claude plugin list`), Python version and the exact phrase or command. A failing case that fits
   in `tests/repo_fixtures.py` is the best reproduction: ask for one, or write it.
3. **Close or accept.**
   - **Close** with the reason in one line: a duplicate (link it), works as documented (link the
     doc), outside what the toolkit does ([GOVERNANCE.md](../GOVERNANCE.md#what-does-not-change-by-vote)),
     or a question (convert it to a Discussion in **Q&A** instead of closing it).
   - **Accept** by removing `needs-triage`. Add `good first issue` when a newcomer can do it from the
     issue text alone, and `help wanted` when anyone may pick it up.
4. **A seat proposal** is decided on the issue under
   [How seat rulebooks are accepted](../GOVERNANCE.md#how-seat-rulebooks-are-accepted). Before
   accepting, check that no catalogue seat, merge group (`MERGES`) or derived role (`DERIVED_ROLES`)
   in `skills/team-setup/scripts/teamlib.py` already covers it, and name the repository signal that
   should raise it.
5. **A security report posted in public**: hide the comment or edit out the details, ask the reporter
   to file it through the Security tab ("Report a vulnerability"), and handle it there under
   [SECURITY.md](../SECURITY.md).

Dependabot's pull requests carry `dependencies` and `ci`; they bump the major version of an action
the workflows use. Merge one once the check run on it is green.

## Reviewing a pull request

**The checks.** The `check` workflow runs on Python 3.9 and 3.12, and `main` requires both jobs to
pass. It runs `check.py`, a fresh scaffold, the skills' commands in order on a new project, the unit
tests and `tools/measure_tally.py --check`. A pull request from a fork runs without the private word
list (forks never receive secrets), so before merging one, check it out and run `python3 check.py`
with your local list in place.

**Neutrality.** Read every added line for anything that identifies a real project: a name, a place,
a vendor, a customer, a register code, a path from someone's repository. Examples use the invented app
Tally. Model names appear only in the tier table (`TIERS` in
`skills/team-setup/scripts/gen-team-agents.py`, mirrored in the README and a seated project's
`docs/TEAM.md` §2); a rulebook names tiers. No email address, phone number or street address in any
file.

**The seat contract.** A rulebook change keeps
[skills/team-setup/references/seat-contract.md](../skills/team-setup/references/seat-contract.md):
the seven `## n · ` sections in order, the catalogue's mark on the description and the H1, 130 to 200
lines, a description of at most 700 characters, a bracketed source on every section 2 shift, a reason
on every rule, and hand-off tables that agree on both sides. `check.py` enforces the countable parts;
the reasons and the hand-offs are yours to read.

**The rest of the change.**

- Generated files were regenerated by their tools (`check.py` fails otherwise; see
  [Generated files](#generated-files)).
- `CHANGELOG.md` has a line under `## Unreleased` that says what changed for a user, and the version
  is untouched: it moves only at release.
- Decide the change's size now, while the reasons are fresh: a rule or script behaviour a seated
  project relies on, changed incompatibly, is a major; a new seat, flag or skill is a minor; a fix or
  wording is a patch. Say so on the pull request if it is a major.
- A change to the scan, the planner, the scaffold or the re-evaluation has a test in `tests/`.
- A change to `gen-team-agents.py` or the templates reaches seated projects only when they copy it
  again; the CHANGELOG line says so.

## Cutting a release

A release is a tag on `main`. The release workflow (`.github/workflows/release.yml`) does the
publishing; your part is the notes, the version and the tag.

1. **Read `## Unreleased` in `CHANGELOG.md`** and edit it into lines a user understands. Pick the
   version from the sizes above: the largest change decides it.
2. **Bump.** From the repository root:

   ```bash
   python3 tools/bump_version.py X.Y.Z            # dated today; --date YYYY-MM-DD to set it
   ```

   It moves the Unreleased entries under `## X.Y.Z — date`, leaves `## Unreleased` with
   `Nothing yet.`, sets the version in `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`
   and `CITATION.cff` (with its `date-released`), and regenerates `docs/facts.json`. It refuses a
   version that is not greater than the current one, an empty Unreleased section, and a repository
   whose versions already disagree. It names any README or `docs/how-it-works.md` line that still
   states the old version: update those by hand.
3. **Run every check:**

   ```bash
   python3 check.py
   python3 -m unittest discover -s tests
   python3 tools/measure_tally.py --check
   claude plugin validate .
   ```

4. **Commit and push `main`:**

   ```bash
   git add CHANGELOG.md .claude-plugin/ CITATION.cff docs/facts.json README.md
   git commit -m "release: X.Y.Z"
   git push origin main
   ```

   Wait for the `check` run on that commit to pass before tagging.
5. **Tag and push the tag:**

   ```bash
   git tag -a vX.Y.Z -m "agent-team X.Y.Z"
   git push origin vX.Y.Z
   ```

6. **The workflow publishes.** It checks that the tag equals `plugin.json`'s version, runs
   `check.py`, the unit tests and `measure_tally.py --check` on the tagged commit, takes the
   `## X.Y.Z` section of `CHANGELOG.md` as the notes (`python3 tools/bump_version.py --notes X.Y.Z`
   prints them locally), and creates the GitHub Release "agent-team X.Y.Z". Follow it with
   `gh run watch` or in the Actions tab.
7. **Users update** with:

   ```bash
   claude plugin marketplace update agent-team
   claude plugin update agent-team@agent-team
   ```

   An install stays on the version it has until `plugin.json`'s version changes, which is why every
   release goes through the bump.

**When the workflow fails.** A tag that does not match the version, or a red check, publishes
nothing. Delete the tag (`git push --delete origin vX.Y.Z` and `git tag -d vX.Y.Z`), fix `main`, and
tag again. Once a release is published, its tag stays where it is: a fix ships as the next patch.

## The private word list

`check.py` sweeps every text file for words that must never appear in this repository: the names,
places, people and vendors of the private projects the rulebooks were first written in. The list
itself is private, so it is never committed, never pasted into an issue, a pull request or a log, and
never quoted in a commit message.

- **On your machine** it is `.private/leak-words.txt` (the `.private/` folder is gitignored), one word
  per line, `#` for a comment. `AGENT_TEAM_LEAK_WORDS=/path/to/list python3 check.py` reads a list
  from anywhere else.
- **In CI** it is the repository secret `AGENT_TEAM_LEAK_WORDS`, the same words one per line. Both
  workflows write it to a temporary file, mask every word in the log, and point `check.py` at the
  file. When the secret is empty (a fork's pull request, or before it is set) the step does nothing
  and `check.py` runs its generic checks only. A path set in `AGENT_TEAM_LEAK_WORDS` that is not a
  file fails `check.py`, so a broken secret step never passes silently.
- **To set or update the secret** from your local list:

  ```bash
  gh secret set AGENT_TEAM_LEAK_WORDS --repo fauzulkc/agent-team < .private/leak-words.txt
  ```

- **A match in CI** shows as `***` in the log, because the words are masked. Run `python3 check.py`
  locally to see the file and line, then change the line.
- **Add a word** the day a project's name could reach the repository, in both places.

## Generated files

These files are written by tools and never by hand. `check.py` fails when one is stale and prints
the command that fixes it; each tool takes `--check`, which exits 1 without writing.

| File | Tool | Built from |
|---|---|---|
| `docs/seats.md` | `python3 tools/gen_seats_md.py` | the catalogue, the rulebooks' descriptions, `MERGES`, `DERIVED_ROLES`, the planner run on the test fixtures |
| the generated files of `examples/tally/` | `python3 tools/build_tally_example.py` | a fresh scaffold run (its docstring lists which files it owns) |
| `docs/facts.json` | `python3 tools/export_facts.py` | the catalogue, the skills' and rulebooks' descriptions, `MERGES`, `DERIVED_ROLES`, `TIERS`, `plugin.json`, `marketplace.json` |
| the version in `plugin.json`, `marketplace.json`, `CITATION.cff`, and the release headings of `CHANGELOG.md` | `python3 tools/bump_version.py X.Y.Z` (`--check` verifies) | the version you give it |

`tools/measure_tally.py --check` is a check, not a generator: the figures `examples/walkthrough.md`
states are kept by hand in its `WALKTHROUGH` table, and it fails when the scripts give different ones.

## The fact sheet

`docs/facts.json` is the data source for the project page and for posts about the project. Anything
outside the repository that states a seat count, a seat's mark, the install commands or the version
reads it from here instead of copying it.

- **Its keys:** `name`, `version`, `license`, `repository`, `homepage`, `description`, `install`
  (`plugin`, `manual`, `update`: each a list of commands), `skills`, `seats`, `merged_seats`,
  `derived_roles`, `tiers`, `counts`.
- **Keys are stable.** Adding a key is fine. Renaming or removing one breaks whatever reads the file,
  so it needs the reader changed first and counts as a major change for the fact sheet.
- **Read it from a tag** for released facts:
  `https://raw.githubusercontent.com/fauzulkc/agent-team/vX.Y.Z/docs/facts.json`. On `main` it can
  carry seats or wording not yet released, under the last release's version.
- **It is byte-stable:** no timestamp, so `export_facts.py --check` compares it exactly.

## Repository settings

`tools/github_setup.sh` sets the repository up from files in this repo, and is safe to run again. With
no flag it prints every `gh` call and writes nothing; `--apply` makes them; `--repo OWNER/NAME` points
it at another repository (default `fauzulkc/agent-team`). It needs `gh` signed in as an admin.

It sets the description (from `docs/facts.json`), the homepage and the topics; turns on issues,
Discussions and private vulnerability reporting; creates or updates every label in
`.github/labels.json`; and protects `main`: the `check` workflow's jobs must pass (their names come
from the workflow's Python matrix), no force pushes, no deletion. Admins may bypass the protection,
so a single maintainer can push a release commit and is never locked out. A label is changed by
editing `.github/labels.json` and running the script again.

## First publish

Each step is the owner's to take.

0. **Commit the working tree** with `python3 check.py` green, so the sweep and the squash below
   cover the final files.
1. **Sweep the whole history, not only the files.** Every commit becomes public, and `check.py` reads
   only the working tree. With your list in place:

   ```bash
   words=$(mktemp)
   grep -v '^#' .private/leak-words.txt | sed '/^[[:space:]]*$/d' > "$words"
   git grep -I -i -w -l -F -f "$words" $(git rev-list --all)   # files, by commit
   git log --all --format=%B | grep -i -w -F -f "$words"       # commit messages
   git log --all --format='%an <%ae>' | sort -u                # authors, public once pushed
   rm "$words"
   ```

   The first two print nothing when the history is clean. A hit in an old commit means publishing a
   rewritten or squashed history instead. The third lists every author name and email the history
   carries.

   **If either shows something that must not go public, publish a squashed history** under the
   GitHub no-reply address (the tree is unchanged; only the history and the author change):

   ```bash
   git checkout --orphan public && git add -A
   git -c user.name="Fauzul Chowdhury" -c user.email=24224476+fauzulkc@users.noreply.github.com \
     commit -m "agent-team 1.3.0: seat an AI team in any project"
   git branch -M public main
   git config user.email 24224476+fauzulkc@users.noreply.github.com   # for every later commit
   ```
2. **Create the repository** on GitHub as `fauzulkc/agent-team`, public and empty:

   ```bash
   gh repo create fauzulkc/agent-team --public --source . --remote origin
   ```

3. **Set the secret** before the first push, so the first run sweeps the private words:

   ```bash
   gh secret set AGENT_TEAM_LEAK_WORDS --repo fauzulkc/agent-team < .private/leak-words.txt
   ```

4. **Push `main` and the tag** of the current version:

   ```bash
   git push -u origin main
   git tag -a v1.3.0 -m "agent-team 1.3.0"
   git push origin v1.3.0
   ```

5. **Apply the settings:** `tools/github_setup.sh` to read what it will do, then
   `tools/github_setup.sh --apply --no-homepage` while the project page is not live yet.
6. **Check the Actions runs:** `check` is green on both Python versions, and `release` created the
   GitHub Release for the tag. Install from the published repository in a clean session, with the
   commands in the README, to confirm the plugin loads.
7. **Once the project page is live**, add its link to the README and run
   `tools/github_setup.sh --apply` again to set the repository's homepage.
